# CharacterMaker V2 - правила разработки

Эти правила обязательны для ветки `refactor/domain-catalog-v2` и всех следующих V2-веток.

## 1. Документация и журнал изменений

Каждое изменение кода, схемы БД, инфраструктуры, API, доменной модели или UI должно сопровождаться обновлением документации в Git.

Минимум для каждого изменения:

- понятный commit message;
- запись в `docs/CHANGELOG.md`;
- обновление профильной документации, если изменились архитектура, схема данных, API, media flow, UI/UX или deployment;
- для миграций БД - SQL-файл в `supabase/migrations/` с тем же смыслом, что примененная migration в Supabase;
- для потенциально рискованных изменений - предварительный backup и запись о нем в `docs/backups/`.

Документация должна описывать фактическое текущее состояние, а не старый или планируемый вариант.

## 2. Текущая продуктовая модель

На текущем этапе CharacterMaker является личным инструментом без пользовательских аккаунтов и ролей.

- все активные пресеты находятся в общей публичной библиотеке;
- основные сущности: `Персона`, `Образ`, `Сцена`, `Результаты`;
- структурированные данные хранятся в Supabase PostgreSQL;
- изображения физически хранятся на InfinityFree в `/media/...`;
- Supabase хранит metadata и связи файлов;
- Cloudflare Workers AI разрешен как внешний генерационный backend, но не как storage и не как источник данных пресетов;
- Cloudflare API Token запрещено коммитить в Git, включать в публичный frontend bundle или сохранять в публичной БД;
- R2, Supabase Storage и платные внешние backend-сервисы не используются;
- видео не входит в текущую продуктовую модель.

## 3. Единое ядро

Web UI и будущий MCP не должны иметь отдельные несовместимые модели данных.

Они обязаны использовать единые:

- domain types;
- catalog ids;
- validation rules;
- mappers;
- application services;
- asset roles;
- схемы Персоны, Образа и Сцены.

Экспериментальные генерационные providers должны добавляться изолированными адаптерами. До отдельного утвержденного integration change они не должны менять state Персоны, Образа или Сцены и не должны обходить общий Core/MCP contract.

## 4. Совместимость устройств

Frontend проектируется mobile-first и обязан работать на:

- iOS Safari;
- Android Chrome;
- desktop Chrome/Edge/Safari/Firefox.

При изменениях UI необходимо учитывать safe-area, `100dvh`, виртуальную клавиатуру, touch targets, системную тему и мобильную загрузку изображений.
